# Arc 06 — Procedural / Skill Acquisition

Use this arc when the target is to **perform or produce something reliably**, not primarily to understand an existing codebase.

Examples:

- implement a data structure or algorithm;
- learn language syntax by using it;
- write a proof pattern;
- operate a technical tool;
- execute a repeatable analytical procedure.

## Core question

Can the learner perform the procedure, explain the causal/structural reason for its steps, diagnose failures, and transfer the skill to a nearby case?

## Suggested progression

### S1 — Establish the smallest viable performance

Ask for the smallest representative attempt. Prefer an actual artifact when the Mission requires one (code, derivation, proof, command sequence), but do not execute it merely because execution is available.

### S2 — Separate essential structure from hygiene

Vary or remove one element at a time. Ask what should change and why. Use execution only when the concrete result is genuinely uncertain or is itself the learning evidence.

### S3 — Diagnose failure modes

Contrast failures such as wrong output, silent invariant violation, nontermination, compile/type error, or crash when those distinctions matter. The learner should connect symptoms to violated structure rather than memorize patches.

### S4 — Transfer

Change a boundary condition, representation, neighboring structure, or requirement. Require the learner to adapt the procedure rather than replay the original example.

## Evidence expectations

Record whether the learner produced:

- prose reasoning;
- pseudocode;
- code or another concrete artifact;
- executed/verified artifact.

A Mission that requires actual performance should not be completed from prose alone.

## Verification policy

Default to reasoning first. Run/build/test when the result can resolve a material uncertainty, validate the learner's concrete artifact, or expose a mechanism that prose cannot establish efficiently.

Do not turn every procedural-learning turn into a terminal session.
